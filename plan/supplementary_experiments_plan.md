## S1 · 耦合家族扩样（**阻断性**｜✅ 脚本就绪，待服务器执行）

**执行（服务器，A100）**：

```bash
CUDA_VISIBLE_DEVICES=1 bash scripts/run_M4v3_family.sh 2>&1 \
    | tee data/M4v3_$(date +%m%d).log
# 拆卡：ARMS="swegnn" BATCH_SIZE=4 / ARMS="nocons ssgc"
```

**同步到服务器**：`scripts/run_M4v3_family.sh`（新）、`scripts/build_coupled_family.py`、
`scripts/prepare_coupled_family_root.py`（两个修/改，见下）。**数据无需同步**。

**脚本已内置两处修复与一道门禁**（规划时发现的两个缺陷）：
1. **RNG 错位（bug）**：`build_coupled_family.py` 的条件抽样原本发生在
   "npz 已存在 → continue" **之后**，于是任何跳过都会让下一个新场景拿到更早
   索引的参数——`--num 12 → 20` 会让 fam012 拿到 fam001 的参数（重复工况），
   文档里"中断后可原样续跑"的路径同样会重复抽样。已改为**按索引预先抽样**
   （i ≤ 11 的取值不变，旧家族仍可复现），并加 `tests/test_coupled_family_draws.py` 锁死不变量。
2. **报告覆写**：`coupled_family_report.json` 每轮从空列表重建，扩样会抹掉
   既有 12 个场景的记录；已改为按名 upsert、保持排序。
3. **门禁**：runner 的第 2 步会**硬断言** fam012–019 八组参数等于预登记值
   （`(1.3306,1.1869) (1.0299,1.2733) (0.8530,1.4418) (1.8010,0.9030)
   (1.2006,1.0217) (0.6247,1.5168) (1.1449,0.9182) (1.5100,0.9618)`）
   且与既有 11 组不重复；不通过直接退出，不允许在错家族上训练。

**切分**：13/2/5（test = fam000 parity + fam004 最低工况 + fam012 中档 +
fam015 高档 + fam011 最强 1.97；val = fam010 + fam014）。
`prepare_coupled_family_root.py` 新增 `--test/--val`，**默认行为逐字节不变**
（M4 v2 仍可复现），并会在 test < 5 时主动提示 KS 门槛。

**⚠ 数据根共用（规划疏漏，已留档）**：M4v3 与 M4v2 共用
`data/real_cases/coupled_chain_family`，而 `prepare_coupled_family_root.py`
会**覆写该根的 `split.json`**（→ 13/2/5）。影响与还原路径：
- M4v2 的 run 目录 json 与 registry 行不可变，**结论不受影响**；
- v2 的逐场景数值可从各 M4v2 run 的 `eval_test.json` 直接读出（test = fam000 + fam011）；
- v2 切分可随时重建：
  `python scripts/prepare_coupled_family_root.py --test mdx_chain_fam000 mdx_chain_fam011 --val mdx_chain_fam010`
- **唯一陷阱**：日后拿 M4v2 的 run 对该根跑 `evaluate.py --split test` 会静默按 5 场景集算，
  与记录值不可比——M4v2 的结果一律以其 run 目录内的 json 为准，不要重跑评测。

**取回**：`runs/M4v3_*_s*` 全部 run 目录 + `ptbest_*`/`ptema_*` 孪生 +
`runs/results.csv` + `data/M4v3_*.log` + `data/real_cases/coupled_chain/`
（含 8 个新场景与合并后的 report json）。

**默认臂**：`nocons / swegnn / ssgc`（3 臂 × 3 种子）——守恒臂 main 的负结果
已在 v2 家族确立，重跑增益有限；需要时 `ARMS="main nocons swegnn ssgc"`。
**统一 batch 2**：v2 家族混用了 batch 4 与 batch 2（swegnn OOM 后降档），
同一世代内协议不齐；M4v3 所有臂统一 batch，消除这项混杂。

**问题**：家族测试集只有 2 个场景，`summarize_runs.py` 直接报
"no domain with ≥2 models and ≥5 scenarios"，KS 无法执行 → **C3 的全部比较
（×1.24 / ×1.36、定向 vs 对称闭合、最强工况分化）目前都没有统计支撑**，只有
跨种子方差可比。而耦合是收窄后本文的**唯一新颖点**，不能只做 case study。

**目标**：测试集 ≥5 场景（KS 的最低门槛），且保留 fam000–011 与 v1 的可比性。

**方案（推荐 A）**：

- **A. 家族扩样 + 重切分**：`build_coupled_family.py --num 20 --seed 11`（原 12 → 20，
  保持相同参数化扰动 × 工况分布），`prepare_coupled_family_root.py` 切成
  **13/2/5**（test=5）。真值成本：8 个新场景 × ~17.5 min ≈ **2.4 h CPU**；
  训练：3–4 臂 × 3 种子 × ~2.5 h ≈ **22–30 h A100**（batch 2 会翻倍，见下）。
- **B. 仅重切分（不可行）**：12 场景无法切出 5 个测试场景而不牺牲训练集（13→9→…），
  且 fam011 是唯一最强工况，必须留在 test 才能保论证。**排除**。
- **C. 只报 case study**：耦合章限定为"可行性与工程意义"，不宣称任何比较结论。
  **兜底方案**——若时间不允许扩样，正文必须按 C 写，并在局限节明说无显著性。

**执行要点**：

1. `bash scripts/run_M4v2_ssgc.sh` 与 `run_M4_v2_family.sh` 均已支持断点续跑与
   `ARMS`/`SEEDS` 拆分；扩样后**旧 12 场景的 run 不可混用**（家族变了）→ 新
   run 目录须用新前缀（如 `M4v3_*`），旧工件留档。
2. **显存**：耦合臂 batch 4 在共卡 A100 上反复 OOM（round 6 首轮与 round 5
   swegnn 臂两次踩坑）→ 默认 batch 2，务必在**确认空的卡**上跑 batch 4，
   或直接接受 batch 2 并沿用既有协议披露写法。
3. **验收判据**（预注册）：扩样后
   - flow_mdk（nocons）vs swegnn 在 best 或 ema 协议上 KS p<0.05；
   - flow_mdk vs ssgc 排序不变；
   - fam011（最强工况）仍复现"浅层恶化至 1.90 m 档"。
   三条任一不成立 → 按 C 方案降级写法。

## S2 · 二维更大域子集（**阻断性**｜✅ 脚本就绪，待服务器执行）

**执行（服务器）**：

```bash
NUM=24 bash scripts/run_2d_larger_domain.sh 2>&1 \
    | tee data/2d_larger_$(date +%m%d).log
# 可选：再补一组在大域上训练的臂（独立 root，~15 h A100）
TRAIN=1 bash scripts/run_2d_larger_domain.sh
```

**同步到服务器**：`scripts/run_2d_larger_domain.sh`（新）、
`scripts/generate_scenarios_2d_family.py`（参数化）。
**数据无需同步**：场景与真值都在服务器现生成（TELEMAC 镜像在服务器）。

**脚本已内置**：
- 生成 128×128 @ 100 m = **12.8×12.8 km**（对齐 SWE-GNN dataset 3 的域尺寸与 g=128），
  `--split-mode generalization` → `split.json` 全部归 `test`，整根即泛化集；
- 真值挂载幂等（按 `meta.solver` 跳过已完成），支持中断续跑；
- 零样本评测 flow_mdk / swegnn / ssgc / gcn / gat × 3 种子 × last/best 双协议；
- **明确排除 U-Net**：128×128=16384 是它 64×64 网格的整数倍，它不会像 65k
  非结构网格那样报错，而是**静默 reshape 成 batch=4** → 结果无意义（已在
  family_meta.json 里写明这条陷阱）。

**成本**：64×64 真值实测 73 s/场景 → 128×128（4 倍单元）估 5–10 min/场景
→ 24 场景约 **2–4 h CPU**；评测约 1 h。

**取回**：`data/scenarios_2d_larger/`（npz + split + meta，约 24×12 MB）、
`runs/MS4_2d_*/eval_test_scenarios_2d_larger.json` 等同名 json、`runs/results.csv`、
`data/2d_larger_*.log`、以及 `data/scenarios_2d_larger/_work/`（真值工作目录，可选）。

**验收判据**：给出「域尺寸翻倍后各模型退化倍数」表；若 flow_mdk 的退化倍数显著小于
浅层骨架，则该轴支持 C1 的机理（感受野/扩散长度与域尺寸的物理匹配）。

**问题**：SWE-GNN 有 dataset 3（12.8×12.8 km、128 网格）作域尺寸泛化；我们原版图
里这一轴由**一维** A3 子集承担，收窄后**完全缺位**——等于对标文献有、我们没有。

**目标**：补一个二维更大域测试子集，与训练域（64×64 @ 100 m = 6.4 km）分离。

**方案**：

- 用现有 TELEMAC-2D 生成流水线（`generate_scenarios_2d_family.py` 同源）生成
  **128×128 @ 100 m = 12.8 km** 场景族（对齐 dataset 3 的域尺寸），建议 20–30 个。
- **最省版本（推荐先做）**：只做**零样本评测**——用已训好的 64×64 模型
  （flow_mdk / swegnn / ssgc / gcn / gat × 3 种子）直接在该子集上评测。
  这检验的正是"训练域 6.4 km → 未见 12.8 km 域"的迁移，与 SWE-GNN dataset 3
  的口径一致，**无需任何新训练**。
- 若要更强的结论，再补一组在 12.8 km 域上训练的臂（3 模型 × 3 种子 ≈ 15 h A100）。

**成本**：真值 20–30 场景 × ~10–20 min（16k 单元/场景，比 4k 单元重）≈ **4–8 h CPU**；
零样本评测 ~1 h。

**验收判据**：价内应能给出"域尺寸翻倍后各模型退化倍数"的表；若 flow_mdk 退化
显著小于浅层骨架，则该轴支持 C1 的机理（感受野/扩散长度随域尺寸的物理匹配）。

**注意**：现 `A3 更大域` 子是**一维**的（`scenarios_partA_v2` 的 A3_test），
不可挪用到二维；两者不可混称。

## S3 · 全时程轨迹证据（✅ 已完成 2026-09-21，**结论推翻了原叙述**）

**脚本**：`scripts/analyze_exam_trajectories.py`（本机 3060 已跑完，序列缓存到
`runs/exam_trajectories_mdx_2d.npz`，改图用 `--refresh` 才重算）。
图件：`G:\论文\260918-FlowMDK\03_图表\fig10_考卷全时程轨迹.png`。

**结果（mdx_2d，探针节点 = 真值水深变幅最大的 3 个节点）**：

| 臂 | 末步 RMSE (m) | 预测峰值/真值峰值 | 判定 |
|---|---|---|---|
| flow_mdk（定向） | 32.16 | **9.48** | 真发散 |
| swegnn（浅层 8 跳） | 21.28 | 6.57 | 真发散 |
| ssgc（对称） | 14.85 | 8.08 | 真发散 |
| -MDK（无扩散分支） | 9.29 | 4.57 | 真发散 |
| gcn（vanilla） | 0.49 | **0.507** | 有界但峰值压低一半 |
| gat（vanilla） | 0.55 | 0.508 | 有界但峰值压低一半 |

轨迹形态：真值先涨到 ~17 m、第 8 步后**回落**并稳在 8–9 m；MDK 系四条在真值
回落之后**仍单调上升**（真发散）；gcn/gat 全程平在 ~8 m，**根本没复现涨-落过程**。

**结论（已据此改写 C2 与全部对外表述）**：
1. **归因仍成立**——发散只出现在 flow_mdk 分裂层 harness 的四个配置上，
   与 MDK 扩散分支、与残差增量解码均无关；
2. **但"vanilla 有界且良好"的说法被推翻**：它们峰值只有真值 ~0.5 倍、输出近乎
   恒定，其低 RMSE 是"真值大部分时间平稳 + 平均指标"的假象；
3. **视野外两边都不可用**（一边不稳定、一边没有动力学）；
4. **新增 C4 素材**：长时程平均 RMSE 会奖励冻结预测——必须配轨迹级证据。

~~**问题**（原记录）：C2 的"边界属算子分裂 harness"此前只有场景级 RMSE 汇总支撑，
无法区分"发散"与"饱和欠反应"。~~

**方案**：写一个诊断脚本，对真实漫滩考卷（`exams_2d`）跑 rollout 并**逐时步
保存探针节点的水深序列**（或在若干代表性节点上存全时程曲线），对比：

- `MS4_2d_flow_mdk_s*`（发散）
- `MS4_2d_gcn_s*` / `MS4_2d_gat_s*`（有界）
- `L16_mdkoff_2d_s*`（无扩散分支，同样发散）
- 真值（TELEMAC-2D）

**产物**：F10 的右图（探针节点水深–时间曲线，四组 + 真值）。

**判据**：若 MDK 系曲线表现为单调漂移/指数放大且最终远离真值，而基线维持有界
振荡 → "发散"成立，机理写作"绝对状态耦合在 OOD 上长程放大"；若基线表现为
被压平/欠反应（曲线几乎不动） → 有界性的解释改为"饱和"，结论要相应改写。
**这一刻的判断会改变 C2 的措辞，必须做。**

**成本**：~0.5 h（复用 `flow_mdk.eval.rollout`，本机 3060 可行）。

## 并发执行注意（S1 与 S2 同时跑时）

- **docker 安全**：`run_telemac2d_docker.py` 用 `docker run --rm -v <workdir>:/work`
  且**不指定 `--name`**，容器名自动唯一，工作目录各自挂载——两端不会撞容器。
- **CPU**：S1 真值 `ncsize=4` + S2 真值 `ncsize=1` 同时跑，约 5 核；≥8 核机器无碍，
  小机器/共享机器只是变慢。
- **GPU（最需要注意）**：S1 的 22–45 h 训练与 S2 阶段 3 的 ~1 h 零样本评测若落在
  同一张卡上，会与共卡负载叠加（round 6 的 batch-4 OOM 就是共卡所致；M4v3 已降到
  batch 2 约 20 GB，仍是全流程最重的作业）。建议 S2 评测换一张卡，或排在 S1 训练
  开始之前跑完。**不要在 S1 训练期间同时开 S2 的 `TRAIN=1`**（两个训练作业会打爆显存）。
- **时间线**：两边前置都是 CPU 真值（S1 ~2.4 h / S2 2–4 h），GPU 阶段天然错开；
  若 S2 真值先结束，其评测会落在 S1 的 CPU 期间——这是最理想的相位。
- **registry**：两端并发向 `runs/results.csv` 追加行（单行 append，风险低）；两轮
  全部结束后再跑一次矩阵重生成即可。
